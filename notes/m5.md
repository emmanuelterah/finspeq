# M5 — Hot path, decision ledger, and the race: results

- **Date:** 2026-11-27
- **Setup:** one Windows machine (Intel Core i7, 32 GB RAM) runs the API, the load generator, the
  feature worker, and Docker (Redpanda, Redis, Postgres). One topic with 4 partitions, warmed with
  one day (2026-03-09, 14,169 events). Model `2e632818a205`.
- **How:** `bash scripts/m5_drills.sh` (broker-down step rerun with `STEPS="2 7"`); raw reports
  in `notes/m5/`
- **Status:** complete, with one exit criterion missed on this machine: p99 < 50 ms holds at
  100 requests/s, not at 500 (section 2).

## 1. What was built

| Piece | Behaviour |
|---|---|
| `ScoreTransaction` | Read the card's window, compute features, predict, decide, publish, and only then answer; per-step timings in metrics and a `Server-Timing` header |
| `POST /score` (`finspeq-serve`) | FastAPI, sync route in the thread pool; 422 for a domain rule, 503 for a store or broker failure, 500 otherwise; `/healthz`, `/readyz` (model, Redis, broker), `/metrics`; 1,000 warm-up predictions at start |
| `ConcurrentPublisher` | One producer per process, a delivery-report thread, one future per request; the wait outlasts `message.timeout.ms`, so a 503 means the event never reached the log |
| Read-your-writes (option A) | `--read-your-writes`: after the log ack the API also writes the event to Redis (`append_event.lua`, no position); the worker later skips it as a duplicate |
| `PostgresLedger` | One transaction per batch: advisory lock, position check, `INSERT ... SELECT unnest(...) ON CONFLICT (tx_id) DO NOTHING`, position upsert; same contract as `MemoryLedger` |
| `finspeq-stream ledger` / `verify-ledger` | Ledger worker on the shared consumer loop; verification reads the whole topic and compares |
| `scripts/load_test.py` | Open-model generator (aiohttp): latency from each request's scheduled time; per request, the card's earlier events missing from the window the API read |

The first load test used httpx and stalled at 53 requests/s with the client, not the server,
as the bottleneck: on the sandbox, httpx reached 160 requests/s against 934 for aiohttp
against the same app. The generator uses aiohttp, and the API uses `uvicorn[standard]`.

## 2. Latency under load

### One API process, producer linger 1 ms

| Target | Achieved | p50 | p95 | p99 | Errors |
|---|---|---|---|---|---|
| 100/s | 100/s | 7.4 ms | 26 ms | **39 ms** | 0 |
| 250/s | 250/s | 9.5 ms | 137 ms | 591 ms | 0 |
| 500/s | 311/s | 8.9 s | 17.4 s | 18.2 s | 0 |
| 750/s | 372/s | 14.2 s | 28.8 s | 30.2 s | 1,021 client time-outs (30 s) |

One API process saturates at about 310–370 requests/s on this machine. Two and four uvicorn
workers at 500/s reached 403/s and 399/s with multi-second latency: the machine, which also
runs the load generator and Docker, is out of CPU. **The 500/s target is not met here.**

### Where the time goes (100/s, medians and p99)

| Step | Budget | p50 | p99 |
|---|---|---|---|
| Redis window read | 2 ms | 1.47 ms | 4.9 ms |
| Features (pure Python) | 1 ms | 0.06 ms | 0.14 ms |
| ONNX predict | 3 ms | 0.44 ms | 1.2 ms |
| Publish and broker ack (linger 1 ms) | 5 ms | 11.3 ms | 19.1 ms |

Everything but the publish is inside budget. The publish is the largest step and depends on the
producer's linger:

| Linger (250/s) | Publish p50 | Publish p99 |
|---|---|---|
| 0 ms | **4.5 ms** | 45 ms |
| 1 ms | 8.0 ms | 50 ms |
| 5 ms | 13.8 ms | 45 ms |

With one request per message there is nothing to batch, so linger only adds waiting. The API's
default linger is now 0.

## 3. The race: reading before the previous write lands

### How often it matters in the data (`card_gaps.json`)

| Previous same-card transaction within | Legitimate | Fraud |
|---|---|---|
| 1 s | 0.014% | 0.047% |
| 10 s | 0.10% | 0.32% |
| 60 s | 0.58% | 1.9% |
| Median gap | 2.7 h | 55 min |

### Same-card bursts (150 cards × 10 transactions, gap between a card's sends)

| Gap | Stale reads, single writer | Stale reads, read-your-writes |
|---|---|---|
| 10 ms | 76% (max 8 missing) | 30% (max 5) |
| 50 ms | 69% | 17% |
| 100 ms | 61% | 15% |
| 250 ms | 45% | 16% |
| 500 ms | 5.1% (max 1) | **0%** |

Read-your-writes adds one Redis call: `append` took 3.2 ms (p50) and 14–26 ms (p99). It removes
staleness only when the previous request has finished; at gaps shorter than the request time,
both requests are in flight and neither can see the other. With a single writer, the feature
worker needs about half a second to apply an event (most of it the consumer's 0.5 s poll wait).

Replaying history at 100 requests/s over 155 cards makes every card transact every 1.5 s on
average, so 23% of those reads were stale; that rate is an artifact of the replay speed, not of
real traffic, where under 0.05% of transactions follow their card's previous one within 1 s.

### Decision

Keep a single writer and measure staleness (ADR-013). Read-your-writes stays available as a
flag. It costs a second writer per card and 3 ms per request, and it helps only for a card
whose transactions come more than one request time apart yet less than about half a second
apart: well under 0.1% of real transactions.

## 4. Broker down for 10 s at 200 requests/s

| | Result |
|---|---|
| Requests | 18,000 |
| 503 `publish_failed` | **80** (0.44%), all scheduled in the second the broker went down |
| Other requests during the outage | Waited and then succeeded once the broker was back; p95 12.6 s, max 15.2 s |
| After restart | Every request answered 200 |

The 80 failures are two rounds of the 40 thread-pool threads, each waiting out the 5 s
`message.timeout.ms`. While those threads were busy, new requests queued in the server instead
of failing, and they completed after the broker returned. No decision was returned without a
log entry. Decision: answer 503 and never return a decision the log does not hold (ADR-014).

## 5. Decision ledger under crashes and a Postgres SIGKILL

| | Result |
|---|---|
| Ledger worker runs | 44: 42 crashes after apply, 1 failure while Postgres was down, 1 clean finish |
| Log events read | 138,315 (14,169 raw warm-up events, the rest scored) |
| Scored transactions in the log | 124,146 |
| Ledger rows | 124,146; `count(DISTINCT tx_id)` = 124,146 |
| Missing / extra / wrong position / position behind | **0 / 0 / 0 / 0** |

The ledger holds 467 more decisions than the load tests counted as answered: those are
requests the 750/s run gave up on after 30 s, which the API still scored and logged. A client
time-out does not cancel a decision; the log and the ledger are the record.

## 6. Not done

- Async route with `redis.asyncio` (the sync route in the thread pool was kept).
- CPU per process was not recorded; the load generator shared the machine with the API.
- Retraining with simulated staleness (option B as written in the roadmap) was not needed: the
  measured staleness affects under 0.1% of real transactions.
