# M6 — Operations: drift, delayed labels, a shadow model, Kafka transactions: results

- **Date:** 2026-11-27
- **Setup:** one Windows laptop runs the API, the load generator, the feature worker, and
  Docker (Redpanda, Redis, Postgres, and the `observability` profile: Prometheus and Grafana).
  Live model `2e632818a205`; shadow model `b99362397317` (candidate `v2-sqrt`). Dataset
  `training_v2`: TRAIN Dec 2024 to Dec 2025, VALID Jan to Feb 2026, TEST Mar to mid-Jun 2026.
- **How:** `bash scripts/m6_drills.sh`, run twice. The second run (`notes/m6_run2.log`)
  replaced steps 2–6 after three drill fixes (section 7); step 7 (envelope benchmark) is from
  the first run. Raw reports in `notes/m6/`.
- **Status:** complete. Latency in this milestone's load runs is not comparable with M5
  (section 3).

## 1. What was built

| Piece | Behaviour |
|---|---|
| `MeasureDrift` (`application/drift.py`) | PSI per feature against a TRAIN reference: decile edges from TRAIN (repeated edges merged), bin shares floored at 1e-4, alert above 0.2 |
| `finspeq-offline drift` | Writes the TRAIN reference and the PSI of every monthly dataset part |
| `finspeq-stream drift-ledger` | Daily PSI of the feature vectors recorded in the ledger; days under `--min-rows` skipped; `--fail-on-alert` exits 1 |
| `label_arrivals`, `RollingRecall` | One seeded chargeback delay per fraud, triangular(7, 21, 60) days; recall over a trailing 30-day window as known on each as-of day, next to the true recall and the share of labels arrived (coverage) |
| `finspeq-offline delayed-labels` | Scores TEST with the ONNX model and writes weekly rolling-recall points |
| Shadow model | `finspeq-serve --shadow-model-dir`: a second model scores the same vector after the live one; its verdict is stored in the envelope and the ledger (`002_shadow.sql`) and never changes the decision. A shadow failure drops only the shadow verdict and increments `fq_shadow_errors_total` |
| `finspeq-stream shadow-report` | Live vs shadow decisions from the ledger, labelled from the event file |
| `scripts/ledger_skew.py` | Joins ledger vectors with the offline vectors of the same `tx_id` and reports, per feature, the share that differ and the PSI of each |
| `experiments/transactional_relay.py` | Consume, transform, produce to an output topic, in `plain` mode (flush, then commit offsets) or `transactional` mode (records and offsets in one Kafka transaction); `count` reads the output with `read_committed` and `read_uncommitted` |
| Observability profile | `docker compose --profile observability up -d`: Prometheus scrapes the API (`:18000/metrics`) and the worker (`:9101`); Grafana loads a provisioned 9-panel dashboard (`infra/grafana/dashboards/finspeq.json`) |
| `scripts/bench_envelope.py` | Encode/decode time and size of the scored envelope: the codec, stdlib `json.loads`, msgspec JSON, msgspec MessagePack |

## 2. Drift

### Offline: each monthly part against TRAIN (`drift_monthly.json`)

TRAIN reference: 9,060,290 rows. Features with PSI above 0.1:

| Month | Split | Features above 0.1 (PSI) |
|---|---|---|
| 2025-03 – 2025-11 | TRAIN | `hour_of_day_utc` 0.16–2.9; `amount_dollars`, `amount_to_max_24h` 0.11–0.14 in Mar–Apr |
| 2025-12 | TRAIN | `tx_count_24h` 0.45, `distinct_merchants_24h` 0.44, `spend_24h` 0.19, `secs_since_last` 0.16, `hour_of_day_utc` 2.9 |
| 2026-01, 2026-02 | VALID | `tx_count_24h` 0.29–0.31, `spend_24h` 0.26–0.27, `distinct_merchants_24h` 0.28–0.30, `hour_of_day_utc` 2.7 |
| 2026-03 – 2026-06 | TEST | `hour_of_day_utc` 2.8–3.8; nothing else |

(2024-12 holds 2,102 rows, the end of the warm-up month, and is left out.)

- `hour_of_day_utc` alerts in 15 of 18 months. The data shows why: in most months nearly all
  transactions fall in one block of UTC hours, either 21:00–08:00 or 09:00–20:00, and the block
  changes over time (April 2025: 99.5% in the night block; April 2026: 99.7% in the day block; July
  2025: one third night, two thirds day). The shift is real, and TEST recall stays at about 93%
  (section 4), so the alert does not mean the model is failing.
- The 24 h count features drift in December to February, the holiday season.

### Live: the ledger's vectors, by day (`drift_ledger.json`)

63 days with at least 200 rows, 180,000 rows in total. Every day alerts: `hour_of_day_utc` (63
days), `secs_since_last` (45), `tx_count_1h` (36), `spend_1h` (35), the 24 h features (32–33).
Offline, the same TEST months alert only on `hour_of_day_utc`. Section 3 shows the extra
alerts come from the serving path, not from the data.

## 3. Shadow model and the serving-path skew

### Live vs shadow decisions (`shadow_report.json`, 90,000 requests, 773 frauds)

| | Live `2e632818a205` | Shadow `b99362397317` |
|---|---|---|
| Fraud flagged (REVIEW or BLOCK) | **89.4%** | 88.7% |
| Legitimate flagged | 0.65% | 0.66% |
| Fraud blocked | 70.1% | 69.6% |
| Legitimate blocked | 0.063% | 0.061% |

The two models gave the same decision for 99.65% of requests. 14 frauds were flagged only by
the live model and 9 only by the shadow. The candidate is not better; the live model stays.
Prometheus counted the same split during the run (live 78,540 / 569 / 527 and shadow 78,532 /
575 / 519 APPROVE / REVIEW / BLOCK over the last 7 minutes).

### Cost of the shadow on the hot path

| Step (p50 / p99) | Live model alone | Live + shadow |
|---|---|---|
| read | 5.5 / 85 ms | 6.6 / 80 ms |
| features | 0.12 / 0.39 ms | 0.13 / 0.38 ms |
| predict | 1.55 / 12.0 ms | 1.75 / 12.8 ms |
| shadow | — | **1.69 / 12.3 ms** |
| publish | 9.0 / 127 ms | 9.6 / 105 ms |
| End-to-end p50 / p99 | 56 ms / 13.3 s | 3.0 s / 15.7 s |

The shadow costs one more predict: about 1.7 ms per request at the median. End-to-end latency
in these runs is queueing, not work: at 200 requests/s the laptop, also running the load
generator, the worker, Docker and the observability containers, was saturated even without the
shadow, which M5 handled at 250/s. These runs also use a 1/16 card slice (M5 used 1/64), so the
window read is larger. The end-to-end figures here are not a latency result; the step timings
are.

### The skew: live vectors vs offline vectors for the same events (`ledger_skew.json`)

| Feature | Live value differs | PSI live | PSI offline |
|---|---|---|---|
| `tx_count_1h` | 12.3% | 0.127 | 0.007 |
| `tx_count_24h` | 15.4% | 0.093 | 0.050 |
| `spend_1h` | 12.3% | 0.110 | 0.013 |
| `secs_since_last` | 14.4% | **0.239** | 0.011 |
| `distinct_merchants_24h` | 14.6% | 0.088 | 0.047 |
| `amount_dollars`, `hour_of_day_utc`, `home_merchant_km` | 0% | equal | equal |
| Any feature | **15.4%** of vectors | | |

PSI here is over all 180,000 rows together, so it is lower than the daily PSI. The share of
vectors that differ (15.4%) matches the stale-read share the load generator measured (13.3% and
17.5% in the two load runs): the API read the card's window before the worker had applied the
card's previous event. Replaying history at 200 requests/s over a 1/16 slice puts a card's
transactions far closer together than real traffic does (M5, section 3). Features that need
no history (`amount_dollars`, `hour_of_day_utc`, `home_merchant_km`) never differ.

So the ledger drift monitor detects training/serving skew as well as data drift. Comparing
live PSI with offline PSI for the same events tells the two apart: `hour_of_day_utc` has the
same PSI in both (drift in the data), `secs_since_last` only in the live vectors (skew).

## 4. Delayed labels (`delayed_labels.json`)

Chargebacks arrive 7 to 60 days after the transaction (triangular, mode 21 days, seed 0).
Recall over the trailing 30 days, at the REVIEW threshold:

| As of | Frauds in window | Labels arrived | Observed recall | True recall |
|---|---|---|---|---|
| 2026-03-31 | 5,524 | 15.5% | 94.1% | 94.3% |
| 2026-04-28 | 5,452 | 15.7% | 93.0% | 93.1% |
| 2026-05-26 | 5,314 | 15.7% | 92.7% | 93.9% |
| 2026-06-23 | 2,683 | 32.1% | 95.0% | 93.6% |
| 2026-07-07 | 212 | 53.8% | 91.2% | 90.6% |

- While data keeps arriving, only 15–19% of the last 30 days' frauds are labelled on any day.
- Observed recall stays within 1.8 points of the true recall at all 15 weekly points. Here the
  delay does not depend on whether the model flagged the fraud, so the labelled frauds are a
  random sample: the delay shrinks the sample, it does not bias it. If caught frauds were
  confirmed faster than missed ones, observed recall would read high; this simulation does not
  model that.

## 5. Kafka transactions vs plain commits (`relay_*.json`)

The relay copies 33,873 events (two days on a 4-partition topic) to an output topic, in batches
of 200. Crashes are a hard exit after the batch is flushed to the broker and before anything
is committed, with probability 0.05 per batch.

| | Plain: flush, then commit offsets | Transactional |
|---|---|---|
| Runs | 11 (10 crashes) | 11 (10 crashes) |
| Output records, `read_committed` | 35,873 | **33,873** |
| Extra copies, `read_committed` | 2,000 (10 batches × 200) | **0** |
| Output records, `read_uncommitted` | 35,873 | 35,873 |
| Extra copies, `read_uncommitted` | 2,000 | 2,000 (the 10 aborted batches) |
| Missing | 0 | 0 |
| Throughput, no crashes | 13,063 and 13,299 events/s | 11,717 and 6,903 events/s |

- Transactions remove the duplicates only for consumers that read with `read_committed`: the
  aborted batches stay in the log and a `read_uncommitted` consumer sees them.
- They cost 10% to 48% of throughput in the two runs (one commit per 200 events; the second
  run's figure varied the most). Larger batches would reduce the cost and add latency.
- Transactions cover only Kafka-to-Kafka. The feature worker writes to Redis and the ledger
  worker to Postgres, which a Kafka transaction cannot include; both keep their positions in
  the store they write (ADR-003). Decision: ADR-015.

## 6. Envelope: JSON vs msgspec (`envelope.json`, 20,000 scored envelopes)

| Per message | Time |
|---|---|
| Codec encode (stdlib JSON + domain types) | 13.7 µs |
| Codec decode (stdlib JSON + validation into domain types) | 37.6 µs |
| stdlib `json.loads` alone | 15.3 µs |
| msgspec JSON encode / decode (typed) | 2.2 / 3.8 µs |
| msgspec MessagePack encode / decode | 1.0 / 3.8 µs |
| Size: JSON / MessagePack | 487 / 456 bytes (−6%) |

msgspec decodes about 10 times faster than the codec. The decode is 0.04 ms against a 9 ms
publish and a 5 ms window read on the hot path, and the M4 workers' limit was the producer, not
decoding. MessagePack saves 6% of the bytes and makes the topic unreadable without a schema.
Decision: the envelope stays JSON (ADR-016).

## 7. Drill fixes between the two runs

1. The relay's transactional mode did not flush before the crash point, so the crashed batch
   never reached the broker and `read_uncommitted` showed 0 extra copies for the wrong reason.
   Both modes now flush before the crash point.
2. The first load run had no baseline without the shadow; step 4 now runs both.
3. Delayed labels listed weeks after the data ended, with no frauds in the window; those points
   are dropped.
4. `scripts/ledger_skew.py` was added after the first run's ledger drift alerts.

## 8. Observability

Prometheus scraped both targets (`finspeq-api`, `finspeq-worker`: up) and Grafana served the
`finspeq` dashboard with 9 panels: decisions/s, step p99, step p50, window entries, events
applied/s, apply latency, late and behind events, lateness p99, shadow decisions and errors.
