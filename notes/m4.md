# M4 — Scaling out: results

- **Date:** 2026-11-26
- **Data:** the M1 slice (card slice 20:0, 115,720 events, 417 cards) for the keyed vs
  round-robin experiment; card slice 4:0 over 2026-03-01 → 2026-06-15 (609,216 events,
  2,178 cards) for scaling, rebalances, the zombie, and live load
- **How:** `bash scripts/m4_drills.sh`; raw reports in `notes/m4/`
- **Status:** complete. Every exit criterion is met; scaling is measured and its limit explained.

All throughput numbers come from one Windows machine (Intel Core i7, 32 GB RAM) running Redpanda,
Redis and up to eight Python workers at once. Two identical single-worker runs measured 6,958 and
12,237 events/s, so single runs vary by up to ±40%. Read the scaling numbers as orders of magnitude,
not benchmarks.

## 1. Tooling added

| Piece | Behaviour |
|---|---|
| `kafka_partitioner.py` | Kafka's murmur2 key partitioner in Python; matches all six values in Kafka's own tests |
| Store `behind` count | Every apply reports stored events earlier than their card's newest time (Lua and memory store, one contract clause) |
| `simulate --round-robin-partitions N` | Ignores the key and sends event n to partition n % N |
| `lateness-sweep --round-robin-partitions N` | Scores events in the order workers would apply round-robin partitions |
| Worker `--assignment-strategy` | `range`, `roundrobin` (eager) or `cooperative-sticky` (incremental assign) |
| Worker `--threads`, `--max-batches` | N consumers in one process; leave the group cleanly after N batches |
| Worker `--stall-s`, `--max-poll-interval-ms` | Sleep once after a poll so the group evicts the worker (zombie test); the eviction is logged, not fatal |
| Worker report | Rebalance timeline, poll vs apply time, apply p50/p99, events behind their card |
| `scripts/lag_monitor.py` | Lag = broker end offset − stored position, sampled every second; drain rate, longest stall |
| `scripts/rebalance_report.py` | Per partition: time from revoke or loss to the next assignment anywhere |

## 2. Keyed vs round-robin publishing (4 partitions, 4 workers)

Keyed values in the last four rows are the in-order reference: keyed partitioning keeps every
card's events in order (first two rows), which is all per-card features depend on.

| | Keyed by card | Round-robin |
|---|---|---|
| Broker partition = Python murmur2 prediction | Yes, every event (integration test) | n/a |
| Events stored behind their card's newest time | **0** of 115,720 | **78,049** (67%) |
| Final windows vs replay (verify-state) | 0 mismatches | **0 mismatches** |
| Feature vectors that differ when scored on arrival (lateness 1 h) | 0 | **77,820** (67%) |
| Decisions that change | 0 | **1,273** |
| Flagged frauds / flag false-positive rate | 890 / 0.52% | 863 / **1.26%** |
| Blocked frauds / block false-positive rate | 755 / 0.058% | **666** / 0.127% |

Without a key, a card's events spread over four partitions that workers apply in parallel, so
two thirds of events reach Redis after a later event of the same card. The final state still
matches a replay, because pruning depends only on each card's newest time; a final-state check
alone would miss the damage. Scoring on arrival is what breaks: every 24 h feature is wrong for
67% of events, the review false-positive rate more than doubles, and 89 fewer frauds are
blocked. The 1 h features are wrong for only 14,909 events, because most reordering spans more
than an hour. Keyed publishing produced zero out-of-order events, as murmur2 predicts.

## 3. Scaling: backlog of 609,216 events

Rate = events applied between the first progress and lag zero, measured by the lag monitor.

| Partitions | Workers | Drain time | Events/s | Apply p50 per batch | verify-state |
|---|---|---|---|---|---|
| 4 | 1 | 86.8 s | 6,958 | 37 ms | |
| 4 | 2 | 52.0 s | 11,592 | 41–43 ms | |
| 4 | 4 | 51.3 s | 11,812 | 96–100 ms | 0 mismatches |
| 4 | 4 threads, 1 process | 44.6 s | 13,501 | 94–101 ms | |
| 8 | 1 | 73.3 s | 8,307 | 25 ms | |
| 8 | 2 | 65.6 s | 9,240 | 50–51 ms | |
| 8 | 4 | 55.0 s | 11,052 | 103–110 ms | 0 mismatches |
| 8 | 8 | 25.1 s | **24,063** | 109–119 ms | 0 mismatches |

- **Scaling is real but not linear.** Eight workers on eight partitions drained 3.5x faster than
  one. Between two and four workers there was no gain, and each worker's own rate fell from
  about 7,000/s alone to about 3,000/s alongside others.
- **Where a worker's time goes (one worker, 4 partitions).** 41% polling and decoding (35.9 s),
  59% applying (51.0 s). Inside an apply, Redis itself spends about 8 ms per 500-event script
  call (`usec_per_call` 7,978, 16 µs per event); the remaining ~30 ms is building arguments in
  Python and the round trip through Docker Desktop's port forwarding.
- **What saturates is the machine, not Redis's data structures.** With four workers, a `PING`
  from inside the Redis container waited 19 to 67 ms on average (peak 219 ms) while Redis held
  only 7.4 MB (peak 9.0 MB). Redpanda, Redis and the port forwarder share the Docker VM's CPUs
  with the workers; adding workers adds waiting, not work done.
- **The GIL is not the limit at this rate.** Four threads in one process (13,501/s) did at least
  as well as four processes (11,812/s): the Kafka client and the Redis socket release the GIL
  while they wait.

### Batch size (one worker, 4 partitions)

| Batch size | Events/s | Apply p50 | Apply p99 |
|---|---|---|---|
| 50 | 5,370 | 4.1 ms | 62 ms |
| 200 | 7,040 | 11.1 ms | 185 ms |
| 500 | 12,237 | 20.7 ms | 51 ms |
| 2,000 | 12,045 | 71.6 ms | 190 ms |

Throughput levels off at 500: past that, one script call holds Redis longer without raising the
rate, and each batch waits longer. 500 stays the default.

## 4. Rebalances: join, join, leave (4 partitions)

Worker A starts; B joins at 6 s; C joins at 12 s; B leaves cleanly after 300 batches.

| | Range (eager) | Cooperative-sticky |
|---|---|---|
| Partitions revoked per change | All of each member's | Only those that move |
| Handoff pauses | 8; median 0.09 s, max 0.76 s | 4; 2.05 s (A → B), 0.07 s (B → C) |
| Time with no partition progressing | 0 s | 0 s |
| Drain rate | 11,326 events/s | 11,946 events/s |
| verify-state | 0 mismatches | 0 mismatches |

Eager rebalancing stops every partition of every member, briefly. Cooperative rebalancing keeps
the partitions that do not move running, but a moving partition waits for a second rebalance
round, about 2 s here. Neither changed the result: positions live in Redis, so a new owner
starts exactly where the old one stopped.

## 5. Zombie: a worker stalls past `max.poll.interval.ms`

Two workers, `max.poll.interval.ms` = 10 s. The stalled worker sleeps 20 s after its 30th poll,
holding a 200-event batch.

| Time | Event |
|---|---|
| 0 s | The stalled worker joins first and owns all 4 partitions; its stall starts about 1 s later |
| 0 s | The peer asks to join; the rebalance waits for the sleeping member |
| +10.0 s | The group evicts the stalled worker; the peer gets all 4 partitions |
| +20.9 s | The stalled worker wakes and applies its old batch: **200 events skipped**, 0 applied |
| +21.5 s | It logs the poll timeout and rejoins |
| +22.1 s | Partitions are split 2 and 2 |
| end | verify-state on 609,216 events and 2,178 cards: **0 mismatches** |

The peer had already applied those offsets, so the zombie's write was a no-op inside the same
Lua call that checks positions. No fencing token was needed.

## 6. Live load: publishing while four workers consume

| Target rate | Achieved publish rate | Max lag | Lag after publishing stops |
|---|---|---|---|
| 5,000/s | 4,995/s | 2,570 events (about 0.5 s) | 0 within 5 s |
| 10,000/s | **6,098/s** (producer limit) | 2,575 events | 0 within 5 s |

The producer, waiting for durable broker acknowledgements of each 1,000-event chunk, could not
exceed about 6,100 events/s; loading the scaling topics with 5,000-event chunks reached 4,337
and 4,532 events/s. The consumers drain at two to four times that rate, so lag never grew: on
this machine the **maximum sustained throughput is about 6,000 events/s, set by the durable
producer**, with consumer headroom of 2x to 4x.

## 7. Decision

Keyed partitioning by card is required, eager `range` assignment stays the default, and
correctness never depends on which worker owns a partition (ADR-012).
